# Tests

Host tests validate contracts that do not require privileged CPU instructions.
`scripts/test-all.sh` runs them, then boots every emulatable target under QEMU
and checks the guest's own output.

| Test | Covers |
| ---- | ------ |
| `host_smoke.cpp` | Physical page accounting |
| `core_services_smoke.cpp` | Formatting, byte streams, block devices, scheduler |
| `platform_model_smoke.cpp` | E820, device tree, and Apple `boot_args` parsing |
| `boot_loader_smoke.cpp` | ELF reading, UEFI memory map conversion, handoff validation |
| `input_smoke.cpp` | PS/2 scancode decoding and the interrupt input queue |
| `device_smoke.cpp` | The device abstraction, the registry's failure cases, and the console's input multiplexing |
| `vfs_smoke.cpp` | Path normalization, the mount table, open/read/write/seek/close, devfs, and block-level device access |
| `file_system_smoke.cpp` | Bounded string helpers, and mounting, walking, listing, and reading the root file system image |
| `heap_smoke.cpp` | The kernel heap: allocation, alignment, merging, ignored bad frees, fragmentation |
| `block_cache_smoke.cpp` | Cache hits, write-back, LRU eviction, pinning, failed write-backs, larger cache blocks, and SHRFS mounted through the cache |
| `exfat_smoke.cpp` | exFAT mounting, case-insensitive lookup, reading, damaged-image rejection, and `mount_device()`, against `images/exfat-basic.img` |
| `partition_smoke.cpp` | CRC-32, MBR with an EBR chain, GPT with its backup header, telling a boot sector from a partition table, and partition device naming |
| `ext4_smoke.cpp` | ext2/ext4 mounting, extent trees, holes, uninitialized extents, indirect blocks up to triple, htree and multi-block directories, symbolic links, meta_bg, rejection of damaged volumes and unsupported features, and exFAT and ext4 mounted together through `mount_device()`, against the three ext images in `images/` |
| `exfat_write_smoke.cpp` | Every kind of exFAT write through the VFS on a copy of `images/exfat-clean.img`, read back step by step; the image it saves is then checked by `tools/check-exfat-image.py` (when CMake finds Python) |
| `virtio_smoke.cpp` | The virtio-blk driver against a fake transport that plays the device: bring-up order, I/O, read-only devices, ring wrap-around, partition publishing |

`images/exfat-basic.img` is generated by `tools/make-exfat-image.py` and kept in
version control, so the host build needs no Python. The generator writes the
image straight from Microsoft's specification and shares no code with the
kernel, so a test fails only when the two read the specification differently.
`shirley-exfat-smoke` also accepts more images on the command line — for
example ones made by `mkfs.exfat` — and checks that each mounts or is refused
cleanly and that its whole tree can be walked.

`file_system_smoke.cpp` and `vfs_smoke.cpp` run against the image the kernel
mounts: the build packs `rootfs/` once and both the kernel and the tests link
the same bytes. A kernel target additionally packs the user program it just
built in as `/bin/hello`, which the host build has no cross toolchain to
produce; that path is covered by the QEMU stage instead.

The QEMU stage boots each target to its shell prompt and then types at it. It
lists the root directory and checks for the entries `rootfs/` really contains,
changes directory and reads a file through a relative path, confirms the prompt
follows the working directory, and reads `uptime` to prove timer interrupts
keep arriving — a count stuck at zero would mean end-of-interrupt is broken.

It also checks the VFS from the outside. `ls /` has to show `dev`, which exists
in no file system and can only come from the mount table; `ls /dev` has to show
the devices the boot log listed; and `blk /dev/ram0 0` has to print the SHRFS1
header, which proves an `open()` followed by a `block_read()` reached the actual
sectors of the disk the root file system is mounted from.

Every target also boots with a virtio disk attached: a 4 MiB image with an MBR
partition table whose first partition holds `images/exfat-clean.img` and whose
second holds `images/ext4-basic.img`. The boot log has to report `vda` with two
partitions, `ls /dev` has to show `vda1`, mounting the whole disk has to be
refused as holding no supported file system, and once `vda1` is
mounted at `/mnt` the stage lists it, reads a nested file and a file named in
the wrong case, and checks `stat`. It then writes: a file created with
`echo >`, read back, a directory made, the file moved into it, a non-empty
`rm` refused, a file deleted, and `sync`. With exFAT still mounted, `vda2` is
mounted at `/e`, `mount` has to show `ext4 (ro)`, and the stage lists it, reads
a nested file and a symbolic link, checks `stat`, sees a write refused, and
unmounts both. Once QEMU has exited the
partition is cut out of the disk image and handed to
`tools/check-exfat-image.py --clean`, which has to find it consistent and
holding exactly the changes the guest made. The disk starts from
`images/exfat-clean.img`, since the damaged entries in `exfat-basic.img` would
rightly fail that check. On ARM the disk is
attached as `virtio-blk-device`, because `-drive if=virtio` would make it a
PCI device there.

The write path is checked the same way round. `echo ... > /dev/uart0` has to
appear in the guest's serial output, which means `vfs::write()` reached the UART
driver; `> /dev/null` must swallow it; and `> /etc/version` must be refused at
`open()` because SHRFS1 is read-only.

The last command is `exec /bin/hello`, which reads a program out of the file
system and hands it to the ELF loader. It takes over the CPU and does not come
back.

On the x86 targets the first line is typed with real key events injected
through the QEMU monitor, so the IRQ1 path is exercised end to end: every
character has to echo and the command has to actually run. ARM64 takes all of
its input over the PL011, which the rest of the typed commands cover.
